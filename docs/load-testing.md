# Нагрузочное тестирование (без AI)

**Цель:** убедиться, что демо выдерживает одновременную работу многих пользователей, и найти узкие места backend. Модель AI в тесте не вызывается: её время ответа (30–60 с) задаёт внешний сервис и от нашего кода не зависит. Настоящие рассылки выключены (`NOTIFY_REAL=false`), чтобы не слать сотни SMS и писем.

## Как запустить

```bash
# backend без фоновых рассылок (SMS и письма не отправляются)
cd backend && NOTIFY_REAL=false NOTIFY_OUTBOX=false NOTIFY_REMINDERS=false LOG_LEVEL=WARNING \
    uv run uvicorn app.main:app --port 8100
# в другом терминале, из корня репозитория
uv run --project backend python scripts/loadtest.py --base http://localhost:8100 \
    --users 10,50,100 --duration 30 --report docs/load-testing-run.md
```

Скрипт — [`scripts/loadtest.py`](../scripts/loadtest.py). Он использует httpx и asyncio, которые уже есть в зависимостях backend, — ставить ничего не нужно.

## Сценарии

На каждом уровне N виртуальных пользователей делятся в пропорции **врач : пациент : менеджер = 5 : 4 : 1**. Каждый входит под демо-аккаунтом и до конца отведённого времени повторяет свой сценарий:

| Роль | Сценарий |
|---|---|
| Врач | очередь → карточка случайного исследования → таймлайн. Каждый пятый круг — новое исследование из протокола и решение без AI; уведомление пациенту создаётся автоматически |
| Пациент | уведомления → свободное время случайного врача → запись → отмена записи |
| Менеджер | дашборд метрик |

**Ошибка** — ответ 5xx или сетевой сбой. Ответ **409** при записи — обычная конкуренция за слот (у пациента уже есть запись на это время). Он считается отдельно и ошибкой не является.

## Стенд

Ноутбук: Intel Core i5-12450H (12 потоков), 16 ГБ, Linux, Python 3.14. Backend — один процесс uvicorn. Генератор нагрузки работает на той же машине и делит с ним процессор. 30 с на уровень, уровни идут подряд на одном экземпляре backend. Данные растут: за прогон врачи создают сотни новых исследований.

### Узкое место и исправление

Профилирование (cProfile, 500 исследований и 1 500 записей) показало: больше половины времени уходило на `Store.list_appointments`. Очередь врача и дашборд для **каждого** исследования искали его записи, уведомление и решение полным перебором — квадратичная сложность.

| Запрос, 500 исследований | До | После |
|---|---:|---:|
| `GET /studies` — очередь | 35 мс | 9,5 мс |
| `GET /metrics/dashboard` | 42 мс | 4 мс |

Исправление — индексы в `backend/app/store.py` по полям связей: решение по исследованию, уведомление по решению, записи по пациенту, врачу, уведомлению и кабинету, аудит по объекту. Они заполняются в `add_*`, поведение API не изменилось, все 140 тестов проходят.

## Выводы

- **При 100 одновременных пользователях ошибок нет**, медиана ответа — 0,3 с. Для демонстрации и отделения на десятки врачей этого с запасом хватает.
- Один запрос к очереди на 1 000 исследований обрабатывается за 7–9 мс. Под нагрузкой время растёт из-за очереди к **одному процессу**: хранилище в памяти, поэтому несколько worker'ов uvicorn запустить нельзя.
- **Для эксплуатации:**
  - СУБД вместо памяти и несколько worker'ов;
  - постраничная очередь врача — сейчас отдаётся целиком;
  - вынос генератора нагрузки на отдельную машину для чистых замеров.
